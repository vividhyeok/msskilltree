# Community Meta Layer

`current/`만 앱에서 읽습니다. `data/`, `research/`, `examples/`, 원본 프롬프트는 제공된 v0.992 자료 보관본입니다. 원본 bundle은 런타임에 포함하지 않습니다.

## 이번 구현

- Run 목표·빌드·시간대·직접 확인한 게임 버전을 선택하면 지원마법/조합 추천을 표시합니다. 클래스·궁극기 직접 시너지, 현재 조합과 보유 유물/완성 시너지, 남은 선택 예산을 고려합니다.
- 유물 비교는 게임에 뜬 3~4개 후보만 고르고 실제 선택한 하나를 기록합니다. 기록은 기존 Run Undo·저장·오프라인 복원에 포함됩니다.
- NEED NOW는 확정한 목표 재료가 우선입니다. 재료가 없을 때만 커뮤니티 보조 후보를 최대 2개 표시합니다. 상세 이유와 출처는 접어 둡니다.
- 새 Run은 고정 가나다순입니다. 이전 저장은 찍은 마법 우선 정렬을 유지하며, Run 설정에서 둘 사이를 전환할 수 있습니다.
- 원래의 `getRecommendedPlan`은 성장 효율 경로로 별도 보존합니다. 메타 우선순위를 이 함수의 비용으로 바꾸거나 반대로 섞지 않습니다.

## 판정 경계

`src/engine/`의 레벨·특성·소비·슬롯·선행 조합·특수 효과 규칙은 그대로 사용합니다. Run에 선택적인 `meta` 필드만 추가했습니다. 메타 엔진이 불가능한 조합/지원마법을 권하지 않도록 기존 판정과 잠금을 먼저 확인합니다. 목표의 재료로 쓸 지원마법과 남은 선택 예산을 넘는 후보는 선제 추천에서 제외하고, 개별 근거에서는 기회비용을 설명합니다.

커뮤니티 규칙 중 `kind: community_meta`만 추천에 사용합니다. seed의 `mechanic` 주장을 확정 게임 규칙으로 승격하지 않습니다. 비숍/궁극기 선택으로 기존 엔진의 보호막 잠금이나 효과를 임의 변경하지 않습니다.

우선순위는 관계(core/high/consider/caution), strength, 맥락 충족, 신뢰도 순으로 설명 가능한 범주를 비교합니다. 같은 범주에서만 추가 레벨과 가나다순을 사용하며 정밀 전투 점수는 만들지 않습니다. `pair`는 후보 외 모든 구성원의 보유/선택 조건을 확인하고, `set`은 각각의 후보에 대한 의견으로 처리합니다. 조건들은 AND, 각 조건 배열은 OR입니다. 알 수 없는 조건은 적용하지 않습니다.

`current/integration.json`은 seed와 앱 사이의 명시적 연결입니다. 여기서 목표 용어의 동의/상위 범주, 지원마법의 실제 ID/특성 단계, 의견이 갈리는 규칙, 우선순위 범주와 시너지 근접 정책을 관리합니다. first_60m은 long_survival에도 속하지만 farm은 기록런으로 확장하지 않습니다.

## 부족한 자료 처리

- 시너지 레시피/필요 유물 전체 목록이 seed에 없어 자동 완성 계산을 하지 않습니다. 유물 선택 시 사용자가 게임에서 확인한 시너지 이름·남은 재료 수·고희귀 핵심 재료 보유 여부를 입력한 경우에만 근접도를 반영합니다. 후보 선택 후 시너지 완성을 자동 확정하지 않습니다.
- 유물 목록은 제공된 31개 범위입니다. 추천 근거가 없다는 표시는 낮은 성능을 뜻하지 않습니다. 네이버 카페·Discord 자료를 새로 수집하거나 검증한 것으로 표현하지 않습니다.
- 실험체와 일부 궁극기/클래스 번역은 seed 이름과 영문 별칭을 함께 보여줍니다. 실험체 조건을 적용하는 규칙은 seed에 없으므로 현재는 기록만 보존하고 효과를 추정하지 않습니다.
- 남은 성장 예산은 사용자 입력입니다. 궁극기 예약분/MAX 이후 성장강화를 임의로 레벨 예산에 더하지 않습니다. 실제 `+` 레벨 기록 때만 1회 줄며 특성 수정/목표 지정은 소비하지 않습니다.
- 저장한 빌드는 기존처럼 목표 조합만 보존합니다. 새 Run에서는 이전 유물/시너지/시간대/예산을 초기화합니다.

## v0.993 및 이후 갱신

1. 원본 snapshot은 보관하고 `current/rules.json`, `entities.json`, `archetypes.json`, `phases.json`, `sources.json`을 검증한 자료로 갱신합니다. React 코드는 수정할 필요가 없습니다.
2. 규칙마다 patch와 sourceIds를 유지합니다. 검증 안 된 규칙은 `reviewStatus: unknown`, 폐기한 규칙은 `obsolete`로 표시합니다. 재검증된 규칙은 `still_valid`, 내용까지 고쳤으면 `changed`로 기록합니다. unknown/obsolete 및 활성 버전과 다른 규칙은 추천에서 빠집니다.
3. `current/patch.json`의 targetGameVersion, createdAt, datasetVersion을 갱신합니다. 확인이 끝난 예정 패치는 nextPatchWatch를 다음 일정 또는 null로 교체합니다. 예정일이 지났다는 이유로 출시 사실을 단정하지 않습니다.
4. 새 지원마법/용어/관계가 필요하면 `current/integration.json`에서 연결과 범주를 추가합니다. 시너지 레시피가 확보되기 전에는 자동 추정을 추가하지 않습니다.
5. 실제 게임 규칙이 바뀐 경우에는 별도로 기존 `src-data/magics.json`, `combinations.json`, `rules.json` 등을 검증·갱신합니다. 메타 패치 변경으로 deterministic 데이터가 자동 변경되지는 않습니다.
6. `npm test`, `npm run build`, `npm run test:e2e`를 실행합니다. 메타 테스트는 데이터만 바꿔 추천이 달라지는지, 잘못된 버전/출처/특성 연결이 빠지는지도 확인합니다.

게임 버전 미입력/불일치, 예정 패치 재확인 시점, 30일 이상 지난 자료는 높은 추천 확신을 낮춥니다. 상황별 이유와 원문 출처는 여전히 참고할 수 있습니다. 날짜는 테스트에서 고정하며 운영에서는 기기의 현재 날짜를 사용합니다.

## QA

추가 피드백의 참여 역할은 기존 requirement의 `primary/material/condition`을 `carrier/material/condition`으로 정규화합니다. `completedMagicStates(run)`은 조합 ID, 승계/병합 역할, 양쪽 참여 마법 목록을 반환하며 Meta Recommendation에도 완료 상태를 전달합니다. 승계 원본과 병합 재료는 모두 기존 locks를 유지합니다. 패시브/선행 조합 조건은 병합 재료로 취급하지 않으며, 유물 효과의 승계 여부를 추측하지 않습니다.

A/B/C 목표는 파랑/보라/호박색을 타일·필요 목록·목표·경로·특성창에서 공유합니다. 상태는 별도의 `→ 승계`, `× 병합`, `◇ 조건`, 준비/불가 문구와 형태로 구분하며 선택 포커스는 흰 테두리입니다. 특성창의 이미 병합된 파트너는 원본 7/7 대신 조합 이름과 재사용 불가를 표시합니다.

단위 테스트: seed 참조, 맥락/시간대/Bishop 조건, 기회비용, 수동 시너지 근접도, 버전·유효성, 이전 저장 호환, 고정 배치.

브라우저 QA: 1024×768, 768×1024, 1280×800, 390×844. 실제 설정 → 목표 → 레벨 → 특성 → 유물 비교/기록 → Undo → 새로고침·오프라인 흐름을 확인합니다. 1024×768에서 세 유물 결과를 가로로 비교하고, 목표 3개/재료 6개를 동시에 표시합니다. QA는 빌드된 앱 전용 localhost:4183을 사용해 개발 서버의 서비스워커 부재와 혼동하지 않습니다.

스크린샷은 `test-results/meta-*.png`에 생성되며 Git에는 포함하지 않습니다.
